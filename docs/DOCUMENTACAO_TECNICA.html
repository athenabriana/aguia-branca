1. Visão e proposta de valor

Aplicativo móvel Android nativo que integra a gestão da inovação corporativa do Grupo Águia Branca, conectando três níveis organizacionais — operacional, tático e estratégico — em um único ambiente para capturar, estruturar e acompanhar iniciativas que gerem impacto mensurável.

Eixo central — Conexão Estratégica: toda ideia pode ser vinculada a uma orientação estratégica publicada pelo líder. Esse vínculo amarra os três níveis na mesma narrativa:

  • Líder direciona (publica orientações estratégicas) e acompanha o impacto consolidado.
  • Operador captura ideias do dia-a-dia, idealmente conectadas à estratégia.
  • Gestor cura as ideias usando matriz ICE (Impacto × Confiança × Facilidade), aprova, gera projeto, conduz a execução.
  • O líder fecha o ciclo vendo qual direcionamento dele virou resultado real (ROI por orientação).

3. Arquitetura

3.2 Conceitos transversais

  • Outcome<T> — wrapper Success(T) / Failure(DomainError). Substitui exceptions cruzando a fronteira de Data → Domain.
  • DomainError — hierarquia selada: NetworkUnavailable, PermissionDenied, NotFound, ValidationFailed, Unknown. Mapeada para português na UI via toPtBr().
  • LocalSession — CompositionLocal<AuthSession?>. Provido no MainActivity, consumido em qualquer tela. Permite UI reagir a logout / troca de perfil.
  • RoleGate — composable que pop-stack se a sessão não tem o papel exigido (defesa-em-profundidade junto com regras Firestore).
  • snapshotsAsFlow — extensão sobre Query e DocumentReference. Ignora erros silenciosamente (evita propagar PERMISSION_DENIED ao signOut, que matava o viewModelScope).

5. Regras de segurança (Firestore)

Controle por papel via lookup no documento de usuário a cada requisição (Sprint 2 vai migrar para custom claims, evitando o lookup). 

service cloud.firestore {
  match /databases/{database}/documents {

    function isAuth() { return request.auth != null; }
    function userDoc() {
      return get(/databases/$(database)/documents/users/$(request.auth.uid)).data;
    }
    function role()       { return userDoc().role; }
    function isOperador() { return isAuth() && role() == 'OPERADOR'; }
    function isGestor()   { return isAuth() && role() == 'GESTOR'; }
    function isLider()    { return isAuth() && role() == 'LIDER'; }
    function affected()   { return request.resource.data.diff(resource.data).affectedKeys(); }

    // ... regras por coleção (ver firestore.rules)
  }
}

6. Fluxos críticos

6.1 Cadastro de ideia

  1. Operador toca em "Nova ideia" a partir de "Minhas ideias".
  2. Formulário valida título, descrição, categoria. Categoria é texto livre com chips de sugestão a partir de IdeaCategory (8 opções). Divisão pré-selecionada com a divisão do autor.
  3. Picker de orientação estratégica é opcional. Vincular concede +5 pts bônus.
  4. FirestoreIdeasRepository.createIdea executa transação: cria doc em ideas, credita pontos no autor (10 ou 15), avalia badges.
  5. UI mostra snackbar "+10 pts" ou "+15 pts (10 base + 5 conexão estratégica)" e volta pra lista.

6.2 Aprovação de ideia → projeto rascunho

Executado por ApproveIdeaUseCase em uma única transação Firestore:

  1. Pre-check: impede gestor aprovar a própria ideia (auto-conflito de interesse).
  2. Lê a ideia, marca status = APROVADA, grava reviewerId e reviewedAt.
  3. Cria documento em projects com stage = PLANEJAMENTO e os snapshots:
    • priorityScore ← idea.ice.score
    • reporterId / reporterName ← idea.authorId / authorName
    • responsibleId / responsibleName ← gestor que aprovou (reviewerId / reviewerName)
    • originatingIdeaId ← id da ideia
  4. Cria a primeira entrada na subcoleção updates ("Criado automaticamente a partir da ideia: X").
  5. Credita +50 pts ao operador autor e avalia novos badges.
Por que snapshot em vez de lookup? A ideia pode ser editada ou deletada depois. O snapshot preserva o critério que justificou a aprovação (ICE), o crédito histórico (relator) e o ponto de responsabilidade inicial — independente do que aconteça com a ideia origem.

6.3 Edição do projeto e troca de responsável

  1. Gestor abre o projeto e toca em "Editar".
  2. Formulário inclui um picker "Responsável" com todos os gestores cadastrados (UsersRepository.listByRole(GESTOR)).
  3. Ao salvar, FirestoreProjectsRepository.update gera diff automático de todos os campos relevantes; se responsibleId mudou, registra entrada na timeline ("Responsável alterado de Carlos para Marcia").
  4. Outra edição qualquer (ex: stage = CONCLUIDO) também aparece como mudança auditável.

6.4 Conclusão do projeto → ideia implementada

  1. Gestor edita projeto e seleciona stage = CONCLUIDO.
  2. Após o update normal, CompleteProjectUseCase roda:
    • Se o projeto tem originatingIdeaId, atualiza a ideia para status = IMPLEMENTADA.
    • Credita +200 pts ao autor da ideia.
  3. Analytics: logProjectCompleted(projectId, hasOriginatingIdea).

6.5 Dashboard — impacto por orientação

DashboardComputer (Kotlin puro, testável) recebe ideias + projetos + orientações + filtros e computa:

  • Funil: submetidas → avaliadas → aprovadas → em execução → ROI positivo.
  • KPIs: ROI consolidado, lucro líquido, investimento total, projetos ativos, ganho médio de produtividade, redução total de custo.
  • Sparkline ROI dos últimos 6 meses (esconde quando há < 2 meses com ROI computado).
  • Impacto por orientação: agregação de ideias + projetos por guidelineId, com ROI agregado.
  • Projetos por ROI: lista ordenada.
  • Ranking top 5 de operadores por pontos (mesmo card que aparece nas telas de operador e gestor).

6.6 Sign-out resiliente

Bug raiz fixado: ao deslogar, os listeners ativos do Firestore disparavam PERMISSION_DENIED (as regras exigem auth). O callbackFlow os propagava como exceção, derrubando o viewModelScope e crashando o app.

Fix: snapshotsAsFlow em FirestoreHelpers ignora erros do listener (apenas para de emitir). O SessionManager emite null normalmente, o AppNavHost detecta e navega para Login.

8. Navegação e RoleGate

8.1 Bottom tabs com saveState/restoreState

O AppNavHost expõe um helper navController.navigateTab(route) que aplica popUpTo(start, saveState = true) + launchSingleTop = true + restoreState = true. Resultado:

  • Trocar de aba preserva o scroll/state da aba anterior.
  • Voltar pra aba previamente visitada restaura o estado salvo.
  • System back na home (Dashboard pro líder, Minhas Ideias pro operador, Curadoria pro gestor) fecha o app em vez de reabrir tabs duplicadas.

8.3 RoleGate

Composable em AppNavHost que faz popBackStack() quando a sessão não tem o papel exigido. Protege rotas sensíveis (criar/editar projeto, criar/editar orientação, curadoria) mesmo se alguém digitar a URL/deep link diretamente. Complementa as regras Firestore.

9. Decisões de produto e UX

9.1 Categorias de ideias

Texto livre + 8 chips de sugestão (IdeaCategory): Operações, Atendimento ao cliente, Tecnologia, Comercial e vendas, Pessoas e cultura, Sustentabilidade, Segurança, Inovação aberta. Permite respeitar realidades de cada divisão sem fragmentar em rótulos infinitos.

9.2 Prioridade vs. ROI

Quando o projeto ainda não tem retorno calculado (planejamento/execução), exibimos a Prioridade ICE (snapshot da matriz da curadoria). Quando atinge CONCLUIDO, paramos de exibir o ICE — o ROI fala por si.

9.3 Relator e Responsável

Distinção explícita entre quem teve a ideia (relator, imutável) e quem está conduzindo (responsável, editável). Reflete realidade corporativa: gestores trocam de time, saem de férias, redistribuem portfólio — mas o crédito do operador permanece.

9.4 Curadoria sem fricção

Originalmente havia dois botões na curadoria ("Salvar avaliação" dentro da matriz ICE e "Aprovar" fora). Refatorado: a matriz emite mudanças via onChange, e o botão "Aprovar" salva o ICE atual + aprova em sequência. Um botão só.

9.5 Empty states informativos

Toda lista vazia mostra um título e uma frase explicativa em vez de "Sem dados". Ex.: na curadoria, "Nenhuma ideia para curar — ideias submetidas pelos operadores aparecem aqui para avaliação com a matriz ICE."

9.6 Sparkline condicional

O gráfico "Tendência de ROI (últimos 6 meses)" só aparece quando há pelo menos dois meses com ROI computado. Linhas planas ou pontos isolados são informação enganosa em dashboard executivo.

9.7 Pontos só para quem deve "jogar"

Gestor e líder não veem o próprio score nem o card de regras de pontuação. Suas telas de perfil mostram apenas identidade e descrição do papel — pontos são mecanismo de engajamento operacional, ruído visual para quem não joga.

9.8 Quick login (demo)

Tela de login tem 3 botões abaixo do card principal ("Líder", "Gestor", "Operador") que fazem login direto com credenciais hardcoded. Acelera demonstração e troca de perfil. Sprint 2 remove esse atalho.

10. Testes

20 testes unitários distribuídos em 3 classes (JUnit 4 + MockK + Turbine + kotlinx-coroutines-test):

  • MapperTest — DTO ↔ Domain (Ideia, Projeto, Orientação, Usuário, Update).

12. Setup do projeto Firebase

  1. Criar projeto no Firebase Console.
  2. Registrar dois apps Android: package com.aguiabranca.app (release) e com.aguiabranca.app.debug (suffix usado em buildType debug).
  3. Habilitar Authentication → método Email/Senha.
  4. Habilitar Cloud Firestore em modo produção. Região sugerida: southamerica-east1.
  5. Habilitar Crashlytics e Analytics.
  6. Baixar o google-services.json agregado (contém os 2 apps) e substituir em app/google-services.json.
  7. Publicar regras e índices: 
    npm i -g firebase-tools
firebase login
firebase deploy --only firestore
    Alternativamente: copiar o conteúdo de firestore.rules e os índices manualmente no Console.
SHA-1 do keystore: não necessário enquanto o app usa apenas Email/Senha. Se for adicionar Google Sign-In na Sprint 2, registrar SHA-1 do debug e do release.

13. Carga inicial de dados (seed)

O seed via long-press no logo (presente no commit inicial) foi removido — o ciclo de signOut do Auth durante a criação dos usuários gerava conflito de sessão e estado inconsistente.

A carga de demonstração agora é feita via Firebase REST API a partir de scripts Python externos. Os IDs gerados ficaram registrados no Firestore do projeto demo (não versionados):

  • 3 usuários base: lider@, gestor@, operador@aguiabranca.com (senha aguiabranca123).
  • 5 operadores adicionais com pontuação distribuída (50–320 pts) e badges parcialmente desbloqueadas — popular o ranking top 5.
  • 4 orientações estratégicas (uma por pilar).
  • 15 ideias distribuídas entre todos os status.
  • 5 projetos (1 concluído com ROI positivo, demais em execução/planejamento).

14. Limitações conhecidas

  • Sem testes integrados com Firestore. Use cases que envolvem transações são exercitados manualmente. Sprint 2 traz emulador.
  • Regras Firestore dependem de lookup por requisição. Custo aceitável no porte da Sprint 1; Sprint 2 vai migrar para custom claims.
  • Sem reset de senha ou onboarding fora dos quick-actions de demo.
  • Sem upload de anexos em ideias/projetos (escopo para Sprint 2).
  • Sem internacionalização — UI fixa em português.
  • Notificações push não implementadas.
  • Modo offline depende do cache padrão do Firestore (sem UI explícita de "sincronizando" / "offline").
  • Quick login com credenciais hardcoded — atalho de demonstração, deve sair na Sprint 2.
