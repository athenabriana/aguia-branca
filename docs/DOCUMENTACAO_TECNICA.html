1. Visão geral

Aplicativo Android que conecta três perfis do Grupo Águia Branca no ciclo de inovação:

  • Líder publica orientações estratégicas e acompanha o impacto consolidado.
  • Operador cadastra ideias e pode vinculá-las a uma orientação.
  • Gestor avalia as ideias usando a matriz ICE (Impacto × Confiança × Facilidade), aprova ou rejeita, e gerencia os projetos resultantes.

A ideia que vira projeto e gera retorno aparece na dashboard do líder agrupada pela orientação estratégica de origem. Assim o líder enxerga quais direcionamentos geraram resultado real.

3. Arquitetura

Três camadas: UI (Compose) → Domain (Kotlin puro) → Data (Firestore). A camada de Domain define as interfaces e não conhece nada de Android nem Firebase, então pode ser trocada na Sprint 2 sem afetar o resto.

Dependência sempre de fora pra dentro: UI e Data dependem de Domain; Domain não depende de ninguém.

3.2 Conceitos que aparecem em todo lugar

  • Outcome<T>: envelope Success(T) ou Failure(DomainError). Usado no lugar de throw entre Data e Domain.
  • DomainError: NetworkUnavailable, PermissionDenied, NotFound, ValidationFailed, Unknown. Convertido em mensagem em português pela função toPtBr() na UI.
  • LocalSession: CompositionLocal com a sessão do usuário. Provido no MainActivity e lido por qualquer tela.
  • RoleGate: composable no AppNavHost que volta uma tela atrás se o papel atual não pode acessar a rota.
  • snapshotsAsFlow: extensão sobre Query/DocumentReference. Converte o listener do Firestore em Flow e ignora erros (para não derrubar o ViewModel no logout).
  • UiState: sealed class com Idle, Loading, Success(T) e Error(DomainError). Usado pelas telas que têm carga assíncrona explícita.

5. Regras de segurança

As regras estão em firestore.rules e controlam o acesso por papel buscando o documento do usuário a cada requisição. São a fonte de verdade — mesmo se a UI esconder um botão, o backend rejeita ações não autorizadas. 

service cloud.firestore {
  match /databases/{database}/documents {

    function isAuth()     { return request.auth != null; }
    function userDoc()    { return get(/databases/$(database)/documents/users/$(request.auth.uid)).data; }
    function role()       { return userDoc().role; }
    function isOperador() { return isAuth() && role() == 'OPERADOR'; }
    function isGestor()   { return isAuth() && role() == 'GESTOR'; }
    function isLider()    { return isAuth() && role() == 'LIDER'; }
    function affected()   { return request.resource.data.diff(resource.data).affectedKeys(); }

    // regras por coleção (ver firestore.rules)
  }
}

Além das regras, o ApproveIdeaUseCase faz verificação extra para impedir que um gestor aprove a própria ideia (caso ele também atue como operador).

6. Fluxos principais

6.1 Cadastrar uma ideia

6.2 Aprovar uma ideia (gera projeto)

Tudo acontece em uma transação no Firestore via ApproveIdeaUseCase:

  1. Verifica que o gestor não é o autor.
  2. Atualiza a ideia: status = APROVADA, grava reviewerId e reviewedAt.
  3. Cria documento em projects com stage = PLANEJAMENTO e snapshots da ideia origem:
    • priorityScore ← idea.ice.score
    • reporterId / reporterName ← autor da ideia
    • responsibleId / responsibleName ← gestor que aprovou
    • originatingIdeaId ← id da ideia
  4. Cria a primeira entrada no histórico do projeto.
  5. Credita +50 pontos no operador autor.

A cópia é proposital. Se a ideia for editada ou excluída depois, o projeto ainda preserva o critério que justificou aprovar, o crédito do autor e o ponto de responsabilidade inicial.

6.3 Trocar o responsável de um projeto

  1. Gestor abre o projeto e toca em "Editar".
  2. No formulário aparece o campo "Responsável" com todos os gestores cadastrados.
  3. Ao salvar, o repositório compara campo a campo e, se o responsável mudou, escreve no histórico uma entrada com field = "responsável", from = nomeAntigo, to = nomeNovo.

6.4 Concluir um projeto

  1. Gestor edita e seleciona stage = CONCLUIDO.
  2. Após o salvamento, CompleteProjectUseCase roda. Se há originatingIdeaId, marca a ideia como IMPLEMENTADA e credita +200 pontos no autor.

6.5 Dashboard do líder

DashboardComputer (Kotlin puro, testável) recebe ideias, projetos, orientações e filtros (período + divisão) e calcula:

  • Funil: submetidas → avaliadas → aprovadas → em execução → ROI positivo.
  • KPIs: ROI consolidado, lucro líquido, investimento total, projetos ativos, ganho médio de produtividade, redução total de custo.
  • Tendência de ROI dos últimos 6 meses, em sparkline. Só aparece quando há pelo menos dois meses com ROI calculado.
  • Impacto por orientação: ideias + projetos agrupados por orientação, com ROI agregado.
  • Projetos por ROI: lista ordenada.
  • Ranking: top 5 operadores por pontos.

6.6 Logout sem travar o app

No logout, os listeners ativos do Firestore retornam PERMISSION_DENIED (as regras exigem autenticação). Sem tratamento, o callbackFlow propagaria isso como exceção e derrubaria o viewModelScope, fechando o app. A função snapshotsAsFlow em FirestoreHelpers ignora o erro do listener — o flow apenas para de emitir e o app navega pra tela de login normalmente.

8. Navegação

8.1 Abas com estado preservado

O AppNavHost tem um helper navController.navigateTab(route) que aplica três flags juntas: popUpTo(start, saveState = true), launchSingleTop = true e restoreState = true. O efeito é:

  • Trocar de aba preserva o scroll e o estado da aba anterior.
  • Voltar para uma aba já visitada restaura o estado salvo.
  • O botão "voltar" do sistema na tela inicial fecha o app, sem reabrir abas anteriores.

8.3 RoleGate

Composable no AppNavHost que volta uma tela atrás se o papel atual não pode acessar a rota. Usado em rotas sensíveis (criar/editar projeto, criar/editar orientação, curadoria). Complementa as regras do Firestore.

9. Decisões de produto

9.1 Categoria: texto livre + sugestões

A categoria é um campo de texto livre, mas há 8 chips de sugestão abaixo (Operações, Atendimento ao cliente, Tecnologia, Comercial e vendas, Pessoas e cultura, Sustentabilidade, Segurança, Inovação aberta). Permite padronização quando faz sentido, sem impedir uma categoria nova.

9.2 Prioridade ICE no projeto

Enquanto o projeto não está concluído, mostramos o score ICE da ideia origem como "Prioridade ICE". Serve para o gestor priorizar a fila quando ainda não há ROI calculado. Quando o projeto chega em CONCLUIDO, o ICE deixa de ser exibido — o ROI passa a ser o critério.

9.3 Relator e responsável

Dois campos diferentes no projeto: relator (quem teve a ideia, imutável) e responsável (quem está conduzindo, editável). Reflete o dia-a-dia: gestores trocam de área, saem de férias, redistribuem portfólio, mas o crédito do operador permanece.

9.4 Curadoria sem botão extra

A matriz ICE não tem botão próprio de "salvar avaliação". Os sliders alimentam direto o botão "Aprovar", que salva o ICE e aprova em sequência. Menos cliques.

9.5 Estados vazios com explicação

Em vez de "Sem dados", as listas vazias têm um título curto e uma frase explicando o que faria a tela ter conteúdo. Ex.: na curadoria, "Nenhuma ideia para curar — ideias submetidas pelos operadores aparecem aqui para avaliação com a matriz ICE."

9.6 Tendência de ROI condicional

O gráfico de tendência só aparece com pelo menos dois meses de ROI calculado. Com menos dados, o gráfico passaria informação enganosa (linha plana ou pico isolado) em um dashboard executivo.

9.7 Pontos só para quem participa

Gestor e líder não veem o próprio score nem as regras de pontuação no perfil. Para esses papéis, a tela de perfil mostra apenas a identidade e uma frase curta sobre o papel.

9.8 Botões de demo na tela de login

Abaixo do formulário há três botões ("Líder", "Gestor", "Operador") que entram direto com credenciais de demonstração. Serve para acelerar a apresentação. Sai na Sprint 2.

12. Setup do Firebase

  1. Criar projeto no Firebase Console.
  2. Registrar dois apps Android: com.aguiabranca.app (release) e com.aguiabranca.app.debug (suffix usado no build debug).
  3. Em Authentication, habilitar o método Email/Senha.
  4. Habilitar o Cloud Firestore em modo produção. Região sugerida: southamerica-east1.
  5. Habilitar Crashlytics e Analytics.
  6. Baixar o google-services.json agregado (contém os dois apps) e substituir app/google-services.json.
  7. Publicar regras e índices: 
    npm i -g firebase-tools
firebase login
firebase deploy --only firestore
    Ou colar manualmente o conteúdo de firestore.rules e os índices na interface do Console.

13. Carga inicial de dados

O carregamento de dados de demonstração que existia no app (toque longo no logo) foi removido. Esse caminho criava conflito de sessão no Auth ao tentar criar vários usuários em sequência.

A carga atual é feita por scripts Python externos que chamam a REST API do Firebase. Os dados ficam no Firestore do projeto de demonstração (os scripts não estão versionados):

ColeçãoConteúdo

projects5 projetos (1 concluído com ROI positivo, demais em execução ou planejamento).

14. Limitações conhecidas

  • Sem testes integrados com Firestore. Use cases com transação são exercitados manualmente.
  • As regras dependem de um lookup no documento de usuário a cada requisição. Funciona no porte da Sprint 1; na Sprint 2 vai migrar para custom claims.
  • Não há recuperação de senha nem cadastro de novo usuário pelo app.
  • Sem upload de anexos em ideias ou projetos.
  • UI fixa em português.
  • Sem notificações push.
  • Modo offline usa o cache padrão do Firestore (sem UI específica).
  • Botões de demo na tela de login com credenciais hardcoded — saem na Sprint 2.

15. Sprint 2
